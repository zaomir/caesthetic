# ТЗ для Cursor: пайплайн сбора базы ICP через Apify

## Контекст

Собираем базу медицинских спа в США по заданным городам для двух задач одновременно:

1. **Приоритизированная очередь для ручного прогрева в Instagram** — подписка и реакции на посты за 5–10 дней до холодного письма
2. **Источник данных для персональных отчётов Growth Score** — рейтинг, скорость отзывов, конкуренты

Обе задачи используют один датасет. Ключевое требование: на выходе не сырой список, а **отсортированная очередь**, потому что обрабатывать её будут вручную по 20–30 записей в день.

**Стек:** Python 3.11+, `apify-client`, `pandas`, вывод в Google Sheets и CSV.

---

## 1. Целевой профиль (ICP)

| Признак | Условие |
|---|---|
| Тип | Медспа / эстетическая клиника, инъекционные процедуры |
| Локаций | **Одна** (мульти-локационные — в отдельный файл, не в основную очередь) |
| Отзывов в Google | 40–400 |
| Рейтинг | 4.2–4.9 |
| **Скорость отзывов** | **менее 5 в месяц за последние 90 дней** ← главный фильтр |
| Сайт | Обязателен |
| Instagram | Желателен, влияет на приоритет |

Логика фильтра по скорости: мы продаём устранение утечки. Практика с высокой скоростью отзывов не имеет той проблемы, которую мы показываем в отчёте, — ей нечего предъявить.

### Города (фаза 1)

```
Scottsdale, AZ
Nashville, TN
Charlotte, NC
Tampa, FL
Raleigh, NC
Austin, TX
Naples, FL
Charleston, SC
Greenville, SC
```

Нью-Йорк, Майами, Лос-Анджелес в фазу 1 **не входят** — там конкуренция за внимание владельца слишком высока и разрыв по скорости отзывов не показателен.

## 2. Архитектура пайплайна

```
Stage 1  Discovery          compass/crawler-google-places
   ↓     сырые места по городам и запросам
Stage 2  Review velocity    compass/google-maps-reviews-scraper
   ↓     отзывы за 90 дней → velocity
Stage 3  Instagram resolve  lukaskrivka/google-maps-with-contact-details
   ↓                        + apify/instagram-scraper
Stage 4  Filter & score     локально, pandas
   ↓
Output   outreach_queue.csv + Google Sheet
```

Каждая стадия сохраняет промежуточный результат на диск и умеет перезапускаться с места остановки. Стадии 1–3 стоят денег — повторный полный прогон недопустим.

## 3. Stage 1 — Discovery

**Актор:** `compass/crawler-google-places`
(тот же актор доступен как `apify/google-maps-scraper` — это одна и та же сущность, не запускать оба)

### Запросы

Для каждого города прогнать список:
```python
QUERIES = [
    "med spa",
    "medical spa",
    "botox",
    "dermal fillers",
    "aesthetic clinic",
    "injectables",
]
```

### Критично: обход лимита выдачи

Одиночный широкий запрос упирается в потолок примерно 120 видимых результатов. Обязательно разбивать зону на 4–6 тайлов по ZIP-кодам или районам, иначе теряется большая часть рынка.

Реализовать `city_tiles.json`: для каждого города список подзон.

### Параметры запуска

```python
{
    "searchStringsArray": QUERIES,
    "locationQuery": tile,
    "maxCrawledPlacesPerSearch": 200,
    "language": "en",
    "countryCode": "us",
    "scrapePlaceDetailPage": True,  # нужен website и категории
}
```

### Забираем поля

`placeId`, `title`, `address`, `city`, `state`, `postalCode`, `website`, `phone`, `categoryName`, `categories`, `totalScore`, `reviewsCount`, `url`, `location.lat`, `location.lng`

### Дедупликация

По `placeId`. Одно место может прийти из нескольких запросов и тайлов.

### Детект мульти-локаций

Группировать по нормализованному `title` (нижний регистр, убрать суффиксы и знаки препинания). Если одно название встречается по 2+ разным адресам — помечать все записи `is_multi_location = True` и выводить в отдельный файл `multi_location.csv`.

## 4. Stage 2 — Скорость отзывов

**Актор:** `compass/google-maps-reviews-scraper`

Это самая ценная и самая дорогая часть. Запускать **только по местам, прошедшим предварительный фильтр** Stage 1 (40–400 отзывов, рейтинг 4.2–4.9, есть сайт, не мульти-локация). Иначе бюджет уходит впустую.

### Параметры

```python
{
    "startUrls": [{"url": place_url} for place_url in filtered_places],
    "reviewsSort": "newest",
    "reviewsOrigin": "Google",   # обязательно, иначе подмешиваются сторонние источники
    "maxReviews": 100,
}
```

`reviewsSort: newest` позволяет остановиться, как только дошли до отзыва старше 90 дней — экономит бюджет.

### Расчёт

```python
reviews_90d      = количество отзывов с publishedAtDate за последние 90 дней
velocity_monthly = reviews_90d / 3
```

Дополнительно сохранять: `owner_response_rate` (доля отзывов с ответом владельца) и `avg_owner_response_days`. Это отдельный блок Growth Score и сильный аргумент в письме.

## 5. Stage 3 — Резолв Instagram

Два пути, в порядке надёжности.

### Путь A (основной) — через сайт практики

**Актор:** `lukaskrivka/google-maps-with-contact-details`

Обходит сайты из выдачи Google Maps и вытаскивает контактные данные и **ссылки на соцсети**. Хендл из сайта самой практики — достоверный, ошибок сопоставления нет.

### Путь B (добор) — поиск в Instagram

**Актор:** `apify/instagram-scraper`

Для тех, у кого хендл не нашёлся на сайте. Поиск по `"{название} {город}"`.

Обязательна проверка совпадения перед записью: город в био или в геометке постов, наличие в био ссылки на тот же домен, что и `website` из Maps. Без подтверждения — поле остаётся пустым. **Ошибочный хендл хуже отсутствующего**: ручной прогрев уйдёт не тому человеку.

### Обогащение профиля

`followersCount`, `postsCount`, `biography`, `externalUrl`, `latestPostDate`, `isBusinessAccount`

`latestPostDate` нужен для отсева заброшенных аккаунтов — прогрев мёртвого профиля бесполезен.

## 6. Stage 4 — Фильтрация и скоринг

### Жёсткие фильтры (исключают запись)

```python
40 <= reviews_count <= 400
4.2 <= rating <= 4.9
velocity_monthly < 5.0
website is not None
is_multi_location == False
категория содержит одно из: med spa, medical spa, skin care clinic,
    plastic surgery, dermatology, aesthetic
```

### Скор приоритета (0–100)

Определяет порядок ручной обработки. Веса:

| Компонент | Вес | Логика |
|---|---|---|
| `velocity_gap` | 35 | Разница между медианной скоростью отзывов топ-3 конкурентов в городе и их собственной. Чем больше разрыв — тем нагляднее отчёт |
| `review_band` | 20 | Пик в диапазоне 80–250 отзывов: практика состоявшаяся, но не доминирующая |
| `owner_response_rate` | 15 | Чем ниже доля ответов владельца, тем очевиднее проблема |
| `has_instagram` | 15 | Возможен прогрев перед письмом |
| `ig_active` | 10 | Пост за последние 30 дней |
| `rating_band` | 5 | Пик на 4.5–4.8 |

`velocity_gap` считается **внутри города**: для каждого города берётся медиана velocity по топ-3 мест с наибольшим `reviewsCount`, разница нормализуется.

### Сортировка вывода

По `priority_score` убыв., затем группировка по городу — чтобы прогрев шёл по одному рынку за раз.

## 7. Схема выходных данных

`outreach_queue.csv`:

```
place_id, priority_score, city, state, practice_name, address, phone,
website, google_maps_url, rating, reviews_count, reviews_90d,
velocity_monthly, velocity_gap, owner_response_rate,
avg_owner_response_days, instagram_handle, instagram_url,
ig_followers, ig_last_post_date, ig_verified_match,
top3_competitors, is_multi_location, collected_at, status
```

`status` — рабочее поле, заполняется вручную: `new` → `ig_followed` → `email_sent` → `replied`.

`top3_competitors` — три названия конкурентов из того же города с наибольшим `velocity_monthly`. Используются напрямую в тексте письма и в отчёте.

## 9. Требования к реализации

- **Идемпотентность.** Повторный запуск стадии не создаёт дублей и не перезапускает уже обработанные записи. Состояние — в `data/interim/state.json`
- **Кэш прогонов.** Сохранять `runId` каждого запуска Apify, уметь дочитать датасет из существующего прогона вместо нового
- **Ретраи** с экспоненциальной задержкой на сетевые ошибки, максимум 3 попытки
- **Логирование** в файл: время, стадия, город, число записей, стоимость прогона
- **Dry-run режим** `--dry-run`: считает предполагаемую стоимость без запуска акторов
- **Лимит бюджета:** параметр `MAX_SPEND_USD` в `.env`, при превышении пайплайн останавливается с явным сообщением

## 11. Как потребляется результат — влияет на спецификацию

Очередь обрабатывается вручную с ограничениями Instagram: **20–30 подписок в день** с прогретого аккаунта, на новом — существенно меньше.

Массовые автоматические подписки и рассылка DM по списку приводят к action block, а при повторе — к потере аккаунта. Автоматизация действий в Instagram в этот пайплайн **не входит и не планируется**: он производит данные, действия выполняет человек.

Практическое следствие для спецификации: при 25 подписках в день база в 600 записей — это работа на 24 дня. Поэтому качество сортировки важнее объёма сбора. Если стоит выбор между «собрать больше» и «точнее отранжировать» — выбирать второе.
